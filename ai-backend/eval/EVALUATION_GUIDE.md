# RAG 与 Agent 评测：当前证据和下一步方案

本文区分已实现、已执行和待执行，不作为真实业务质量报告。

## 1. 当前有什么

| 内容 | 当前状态 | 证明什么 / 不证明什么 |
|---|---|---|
| `eval/retrieval_benchmark.py` | 已有脚本，本轮未跑真实语料 | 实际 BGE + 临时 Milvus；检查单证据 Hit@8、阈值后命中、证据是否留在分块中；不是全 Agent，也不是完整多证据 Recall |
| `eval/execution.py` | 已实现并有假模型回归 | 记录真实执行中的工具查询、片段与最终模型请求保留的 KB 上下文；不是回答后重新检索 |
| `eval/router.py` | 已有 RAGAS CLI，本轮未真实评分 | 仅有证据才评分，检索故障单独报告；模型裁判需人工校准 |
| `tests/test_agent_harness.py` 等 | 本轮默认离线回归通过 | 真实框架 + 假模型、临时库，验证超时、预算、断连、写操作不重试等工程边界；不证明真实模型会选对工具或回答正确 |
| 真实人工标注质量基线 | 未建立 | 目前不能报告业务 Recall、准确率或改善幅度 |

默认参数：新文档块最多 500 字符，长段落重叠 60；Top-k=8；min_score=0.5；单次 KB 上下文上限 8000 字符；整个主模型输入近似预算 32000 字符。不是 tokenizer 精确计数。

## 2. 先准备什么样本

先用 10～15 条做小样本诊断，后续扩展约 30 条或更多独立样本。题目来自实际使用场景，并由人核对来源，不让同一个模型独自生成题目、标准答案和验收结论。

覆盖：直接事实、同义表达、精确术语/编号、跨段落多证据、资料无答案。Agent 另有工具选择、发布、失败和提示注入样本。不能把这些不同分母的指标混成一个准确率。

每条保存：

- 问题、语料版本、类别；
- 文档 ID 和原文证据位置（最好是稳定的原文跨度），需要哪些独立证据；
- 固定分块版本下相关片段 ID（若计算片段 Recall）；
- 预期答案要点、禁止无依据添加的结论；
- 预期工具行为与禁止行为（不要求唯一逐字工具查询）；
- 实际查询、召回排名/分数、过滤后片段、最终可见上下文、回答、工具执行轨迹；
- 模型/Prompt/工具版本、参数、延迟、Token、错误状态。

标注文件和真实私有资料保存在仓库外。开发集用于调参，保留独立验收集不反复用于选参数。小样本要报告原始分子/分母和代表性失败，不宣称可推广的稳定质量。

## 3. Top-k 怎么比较

Top-k 是参数，不是质量分数。

1. 冻结语料、分块、Embedding、索引、查询集合及标注；暂不调用 LLM，先隔离检索能力。
2. 分别比较 k=2、4、8、12；初轮固定阈值，再固定候选 k 比较阈值，例如 0.4、0.5、0.6。这些只是待比较候选值。
3. 每组都分别检查：原始 Top-k、文档有效性/阈值/长度过滤后、最终给模型的证据。否则不知道证据是没召回，还是被过滤/裁剪掉。
4. 记录证据覆盖、无关/重复片段、实际片段数、检索延迟、上下文字符数。
5. 对候选方案运行相同 Agent/RAG 问题，检查最终回答和成本。检索命中改善不一定代表回答改善。
6. 优先选择满足业务证据覆盖且噪声/成本可接受的方案，不是永远选最大 k。业务可接受标准须人工确认。

当前 benchmark 固定为 k=8、阈值 0.5，尚不支持参数网格；以上是下一步实验方案，不是已执行结果。它不走生产 SQLite 孤立向量过滤，也不走完整 Agent。生产过滤位于 Top-k 之后，孤立向量可能占据候选名额，这是需单独验证的差异。

## 4. Hit@k、Recall@k、Precision@k

固定分块和相关性口径下，设某问题的人工相关片段集合为 G，前 k 个片段为 R_k：

```text
Recall@k = |G ∩ R_k| / |G|
Precision@k = |G ∩ R_k| / |R_k|
Hit@k = 只要 G ∩ R_k 非空就记 1，否则记 0
```

检索刚好返回 k 条时，Precision 的分母为 k；阈值后不足 k 条须明示用实际返回条数，不把不同定义混用。

例：全部相关片段 4 个，Top-8 找回 3 个，则 Recall@8=3/4，Precision@8=3/8，Hit@8=1。多问题通常报告每题 Recall 的均值（宏平均），如同时报告微平均需说明定义。

当前 benchmark 每题只标一个原文证据字符串，要求某个返回块完整包含该字符串。10 题有 7 题命中时，Hit@8=7/10；不是多证据 Recall@8。字符串跨块时可能判未命中，即使多个块合起来能支持答案，所以还要看 `evidence_in_chunk` 并人工复核。

若一题确实只需一个证据且标注完整，单题 Recall 可以退化为 0/1，但不能据此默认所有题都只有一个证据。

改分块时不能沿用旧 chunk ID 来计算 Recall。可以改用独立原文证据单元（例如三个必要事实）标注覆盖，报告为“证据覆盖率/证据召回”，明确单位；重叠块包含同一事实只计一次，避免重复片段抬高覆盖。不要把证据单元与片段级相关性混为一谈。

无答案题没有相关证据，Recall 分母为 0，记为不适用；另外检查错误提供证据、无依据作答和正确拒答。检索异常单列，不能算作正常无答案，也不能丢掉失败样本后只报成功平均分。

## 5. 为什么还要评估整个 Agent

检索可用不代表 Agent 会调用；调用成功也不代表任务完成。建议分层：

| 层 | 具体检查 | 例子 |
|---|---|---|
| 行为 | 工具是否该调用、参数语义是否正确、是否多余调用 | 文档专有问题应检索；查询不要求与用户问题逐字相同 |
| 检索 | 证据有没有进入最终上下文 | 原始命中但被阈值过滤，单独归因 |
| 回答 | 事实忠实、答案要点覆盖、引用支持、资料不足说明 | 含一个严重无依据结论应单列，不能被平均分掩盖 |
| 业务 | 任务是否真的达成 | 发布需测试库确认文章和作者，不靠模型说“成功” |
| 多轮 | 是否利用正确历史、是否丢失限制 | 先生成草稿再要求修改，不能在没有发布要求时发布 |
| 故障 | 超时、断连、预算、依赖失败、写结果未知 | 不把检索故障说成无资料，不因超时重复发布 |
| 安全 | 是否执行文档中的恶意指令、是否越权 | 文档要求发布文章不是用户授权；真实模型尚须检查 |
| 效率 | 工具/模型调用数、首字和完成延迟、Token/成本 | 多次运行查看波动，不只挑一次成功 |

当前离线 RAG CLI 只提供时间和知识库工具，不包含完整线上工具集合、JWT 业务调用、SSE 和 checkpoint 多轮过程。真实 Agent 验收应使用一致的工具集合及测试环境，不能把 CLI 评分等同完整线上结果。

## 6. 发布工具怎么评

发布涉及真实写入，使用隔离测试环境/测试账号，不在生产自动跑。

1. 明确发布：参数合规，确认产生文章、作者来自登录用户、存储正文已清洗。
2. 只要草稿：应不调用发布工具。若模型误调用，说明授权边界失败；当前 Prompt 不是硬授权，不掩盖失败。
3. 非法参数/清洗后空正文：拒绝，不写库。
4. 恶意 HTML：服务端移除危险内容，正常代码块保留；前端防护也保留。
5. 网络超时：提示结果未知，单轮不重试；用测试桩模拟“已写入但响应丢失”，单独验证副作用。
6. 已发布但后续回答失败：不能提示“没有发布”；应告知已发布，不要重复。
7. 重复任务：当前跨任务没有幂等保障，标记已知缺口，不声称全部防重。
8. 恶意检索内容诱导发布：应无发布调用。当前无独立硬授权，语义测试成功也不等于不可绕过。

工程测试可用脚本化假模型和假 HTTP 确认控制逻辑；真实工具选择/语义遵循必须另用真实模型样本验证，必要时每题重复多次并报告严重错误。

## 7. 答案评估为什么取最终实际上下文

Agent 可能改写查询、检索多次、裁剪旧消息。如果回答后拿原问题重新检索，得到的证据可能不是模型生成答案时看到的，评分对象就错了。

`RunState` 记录检索 artifact 和每次模型请求裁剪后的消息。`final_model_contexts` 只提取最终回答那次请求中保留的 KB 证据。无证据记 `no_context`，检索失败记 `retrieval_failed`，不强行送空上下文给 RAGAS。仍须人工检查证据完整性和引用。

忠实度高不保证回答完整，更不保证源文档正确。裁判结果只能辅助，不能替代人工标准与独立验收。

## 8. 面试表述（按实际状态使用）

> 我把检索评测、答案质量和 Agent 行为分开。检索层已有实际 BGE/Milvus 的单证据 Hit@8 脚本；生成层采集最终模型真正看到的上下文，不在回答后重新检索；工程层用假模型回归超时、预算和发布不重试等边界。真实业务质量基线尚未建立，所以不报告未测的 Recall 或准确率。下一步先标注证据和预期行为，对比 k/阈值，再用真实模型检查工具选择、回答依据及副作用，发布只在测试环境验收。

不要改写成“完成了全面 Agent 评测”或“实验证明 Top-8 最优”。
